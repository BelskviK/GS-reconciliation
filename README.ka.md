# გადახდების შედარების დეშბორდი (Payment Reconciliation Dashboard)

დეშბორდი Bank of Georgia-ს ტრანზაქციების შედარებისთვის აქტიურ მომსახურების ხელშეკრულებებთან — გადახდები ერთვება კომპანიებს, ჩანს დაუდგენელი ტრანზაქციები და შედარებულია მოსალოდნელი შემოსავალი ფაქტობრივთან, თვეების მიხედვით.

**Live:** [gs-reconciliation.vercel.app](https://gs-reconciliation.vercel.app/)

🇬🇧 [English version](./README.md)

## სტეკი

- Next.js 15 (App Router) + TypeScript
- Supabase (Postgres + PostgREST + RPC)
- TanStack Query
- Tailwind CSS v4
- Zod

## გაშვება ლოკალურად

### 1. დამოკიდებულებების დაყენება

```bash
npm install
```

### 2. Supabase პროექტის შექმნა

გადადით [supabase.com](https://supabase.com)-ზე, შექმენით უფასო-ტარიფის პროექტი და დაელოდეთ მის მზადყოფნას.

### 3. SQL ფაილების გაშვება — თანმიმდევრობით, თითო-თითოდ

Supabase-ის დეშბორდზე გახსენით **SQL Editor**. თითო ფაილისთვის გახსენით **ახალი query ტაბი**, ჩასვით შიგთავსი და დააჭირეთ **Run**-ს (რამდენიმე ფაილის ერთ ტაბში ჩასმა მხოლოდ ბოლო statement-ს გაუშვებს). ამ თანმიმდევრობით:

1. `schema.sql` — ყველა ცხრილი, ფუნქცია და ტრიგერი, რაც აპლიკაციას სჭირდება: `companies`/`contracts`/`bank_transactions`, `match_transactions_by_inn()` (ღილაკის **"მატჩინგის გაშვება"** უკან მდგომი ფუნქცია), პლუს არასავალდებულო ledger-ის სქაფოლდი (`financial_events`/`accounts`/`journal_entries`/`journal_lines`, 16-ანგარიშიანი ანგარიშთა გეგმა და ტრიგერები, იხ. [სამსაფეხურიანი ledger-მოდელი](#სამსაფეხურიანი-ledger-მოდელი)). მონაცემები ჯერ არ არის.
2. `seed_contracts.sql` — 15 კომპანია, 18 ხელშეკრულება. თითოეული ხელშეკრულების ledger-მოთხოვნა მაშინვე იწერება insert-ის დროს.
3. `seed_demo_opening_balance.sql` _(არასავალდებულო, მხოლოდ დემოსთვის — რეალურ დეპლოიმენტზე გამოტოვეთ)_ — წერს ledger-ის ფანჯრამდელ ბალანსს, რომ ეკრანზე რიცხვები აქედან საღად გამოიყურებოდეს, ერთი დიდი რიცხვის ნაცვლად შემდეგი ნაბიჯის გაშვებამდე. იხ. ფაილის საკუთარი header და ხუთი-საფეხურიანი ვიზუალი [`docs/ARCHITECTURE.ka.md`](./docs/ARCHITECTURE.ka.md)-ში.
4. `seed_transactions.sql` — 89 საბანკო ტრანზაქცია (აპრილი–ივნისი, 2026), ყველა `unmatched`. თითოეული იმპორტი მაშინვე იწერება insert-ის დროს.

`schema.sql`-ის ledger-ნაწილი (და ზემოთა მე-3 ნაბიჯი) სრულიად არასავალდებულოა — გამოტოვეთ, თუ მხოლოდ სავალდებულო დეშბორდი გაინტერესებთ.

შემოწმება: `select count(*) from bank_transactions;` → 89. `select match_transactions_by_inn();` → 77 (12 რჩება დაუდგენელი — გამგზავნის INN არცერთ სახსენებულ კომპანიას არ ეკუთვნის).

### 4. გარემოს ცვლადების კონფიგურაცია

დააკოპირეთ `.env.local.example` → `.env.local` და შეავსეთ თქვენი Supabase პროექტის URL და anon key (**Project Settings → Data API**):

```
NEXT_PUBLIC_SUPABASE_URL=https://your-project-id.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-or-publishable-key
```

### 5. dev სერვერის გაშვება

```bash
npm run dev
```

გახსენით [http://localhost:3000](http://localhost:3000).

**ნავიგაცია:** `/` არის ledger-რეკომენდაციის ბრენჩის Summary გვერდი (ბალანსი + მოგება-ზარალი), არა სავალდებულო დეშბორდი. ყველა გვერდი იზიარებს ერთ sidebar-ს, სადაც არის ჩარჩოიანი ბმული **"შედარების დეშბორდი" / "ეს არის დავალება"** — `/reconciliation`-ზე, რომელიც არის დავალების რეალური ნაწილი — პლუს ledger-ის საკუთარი ნავიგაცია (`/`, `/accounts`, `/journal`). იხ. [საიდან შეიძლება გაგრძელება](#საიდან-შეიძლება-გაგრძელება) დეტალებისთვის.

**გადატვირთვა:** მატჩინგის თავიდან შესამოწმებლად, `truncate table bank_transactions cascade;` და შემდეგ ხელახლა გაუშვით `seed_transactions.sql`. ხელშეკრულების მოთხოვნის თავიდან შესამოწმებლად (მაგ. `post_contract_demand()`-ის შეცვლის შემდეგ), `truncate table contracts cascade;` და წაშალეთ მისი `financial_events`/`journal_entries` მწკრივები, შემდეგ ხელახლა გაუშვით `schema.sql` + `seed_contracts.sql`.

## სავალდებულო დეშბორდი

ყველაფერი, რასაც დავალება ითხოვდა — ავტო-მატჩინგი (`sender_inn = tax_id`, იდემპოტენტური, `ignored` სტიკი), სტატისტიკის ზოლი, ტრანზაქციების ცხრილი, თვეების ნავიგაცია, მოსალოდნელი-vs-ფაქტობრივი, ძებნა, CSV ექსპორტი, Zod ვალიდაცია და TanStack Query ჩატვირთვის/ქეშირების/მუტაციებისთვის — ცოცხალია **`/reconciliation`**-ზე, აშენებული `schema.sql`-ის `companies`/`contracts`/`bank_transactions` სქემაზე. აქ წერტილ-წერტილ არ არის გამეორებული — კოდი თავად არის ჭეშმარიტების წყარო. ორი რამ ღირს იცოდეთ წინასწარ:

- [სად მდებარეობს მატჩინგის ლოგიკა](#სად-მდებარეობს-მატჩინგის-ლოგიკა) — ეს ბაზის ფუნქციაა, არა კლიენტის კოდი, და ეს არჩევანი შეგნებულია.
- [მოსალოდნელი vs ფაქტობრივი: ძირითადი წესი](#მოსალოდნელი-vs-ფაქტობრივი-ძირითადი-წესი) — ერთი წესი, რომელიც თესლის მონაცემების კიდურა შემთხვევებს მუშაობს.

## სქემა

სრული DDL იხ. `schema.sql`-ში. შეჯამება:

- **companies** — `id`, `name`, `tax_id` (unique)

- **bank_transactions** — `id`, `doc_key` (unique), `entry_date`, `amount`, `sender_name`, `sender_inn`, `matched_company_id` (FK, nullable), `match_method`, `match_confidence`, `status`, `comment`

## სად მდებარეობს მატჩინგის ლოგიკა

ის მდებარეობს ბაზაში, როგორც Postgres ფუნქცია (`match_transactions_by_inn()`), რომელიც გამოიძახება Supabase RPC-ის საშუალებით. ფინანსური შედარება უნდა იყოს სანდო, არა კლიენტის მხარეს; თავად მატჩინგის წესი (`sender_inn = tax_id`) არის ერთი თანასწორობის join, ვერტიკალური ლოგიკის ან გარე გამოძახებების გარეშე — აპლიკაციის კოდს არაფერი ემატება მისი ხელახლა-იმპლემენტაციით.

**რატომ:**

- **ატომურობა** — ერთი SQL statement, ქსელის ხარვეზი შუა ციკლში ნახევრად-დამატჩებულ მდგომარეობას არ ტოვებს.
- **წარმადობა** — ერთი round-trip, N-ის ნაცვლად.
- **იდემპოტენტურობა** — ეხება მხოლოდ `unmatched` მწკრივებს; უკვე დამთხვეული ან ხელით `ignored` მწკრივები არასდროს არ ეხება.
- **ქმედითი შეცდომები** — თუ ფუნქცია ჯერ არ არის შექმნილი, სერვისის ფენა ცნობს კონკრეტულ PostgREST შეცდომას და ღილაკი ოპერატორს ეუბნება `schema.sql`-ის გაშვებას, დუმილის ნაცვლად.

**კომპრომისი:** ეს ლოგიკა უჩინარია მხოლოდ Next.js კოდის მკითხველისთვის. მისაღებია, რადგან პატარა და ერთი-დანიშნულებისაა — ამიტომვეა ხელით მატჩინგი და fuzzy-შემოთავაზებები აპლიკაციაში, არა ბაზაში.

## მოსალოდნელი vs ფაქტობრივი: ძირითადი წესი

ხელშეკრულება ითვლება აქტიურად თვე M-ში, თუ `start_date <= M-ის ბოლო დღე` და (`end_date IS NULL` ან `end_date >= M-ის პირველი დღე`).

- **სეიფ ტრანსპორტი** (`end_date = 2026-05-15`): აქტიური აპრილი–მაისში, გამოვარდნილია ივნისში
- **ურბან მუვერსი** (`end_date = 2026-04-30`): აქტიური მხოლოდ აპრილში
- **ეკო ტრანსპორტი** (ორი პარალელური ხელშეკრულება): მოსალოდნელი თანხა ჯამდება, არ არჩევა ერთი მწკრივიდან

## მონაცემების ჩატვირთვა, ქეშირება და მუტაციები

ყოველი წაკითხვა გადის TanStack Query-ს ცენტრალიზებული query-key ფაბრიკის საშუალებით (`src/lib/query/queryKeys.ts`). კომპანიები/ხელშეკრულებები იყენებენ 5-წუთიან `staleTime`-ს; ტრანზაქციები იყენებენ `staleTime: Infinity`-ს და მთლიანად ეყრდნობა მუტაცია-გამომწვევ invalidation-ს (არაფერი სხვა არ წერს `bank_transactions`-ში, სანამ დეშბორდი ღიაა) — ამიტომ უკვე ნანახ თვე/ფილტრ კომბინაციებზე გადართვა ხდება ქეშიდან, ქსელური მოთხოვნების გარეშე. `placeholderData: keepPreviousData` ინარჩუნებს ცხრილს შევსებულს ახალი კომბინაციის ჩატვირთვისას.

ყოველი ჩაწერა გადის `src/hooks/useTransactionMutations.ts`-ის საშუალებით (`useRunAutoMatching`, `useManuallyMatchTransaction`, `useUnmatchTransaction`, `useUpdateTransactionStatus`, `useUpdateTransactionComment`). თითოეულს შეუძლია ტრანზაქციის სტატუსის შეცვლა, ამიტომ თითოეული აბათილებს მთელ `["transactions"]` key-სივრცეს, ცალკეული ფილტრირებული ხედების წერტილოვანი განახლების ნაცვლად.

## არქიტექტურის შენიშვნები

- **სერვისის ფენა** (`src/services/`): ერთი ტიპიზებული ფაილი თითო ცხრილზე, პირდაპირ Supabase-ს გარშემო — ცალკე repository ფენის გარეშე. `NUMERIC` სვეტები PostgREST-იდან სტრინგებად მოდის და `number`-ად პარსდება სერვისის საზღვარზე, ერთხელ.
- **`src/types/database.ts`**: ხელით დაწერილი, `schema.sql`-ის ასახვისთვის.
- **Zod**: ვალიდაცია ფილტრის/ძებნის/სორტირების მდგომარეობისთვის, `src/schemas/transactionFilters.ts`-ში.
- **ფიქსირებული სვეტების სიგანე**: `TransactionsTable` იყენებს `table-layout: fixed`-ს, რომ გრძელი მნიშვნელობები შემოკლდეს, სხვა სვეტების წანაცვლების გარეშე.

## საიდან შეიძლება გაგრძელება

დღეს ეს აპლიკაცია პასუხობს ერთ კითხვას: _ემთხვევა თუ არა მიღებული საბანკო ტრანზაქციები იმ ხელშეკრულებებს, რომლებზეც გადახდას ველოდებით?_ ეს არის დავალება, და `/reconciliation` მას სრულად პასუხობს.

ამ ბრენჩზე მოცემული რეკომენდაცია არის ის, რასაც სენიორი ინჟინერი შემოგთავაზებდათ შემდეგი მოთხოვნის მოსვლამდე — რადგან ის მოვა: ხელფასები, ქირა, მომწოდებლის ინვოისები, გადასახადები, სხვა განმეორებადი ხარჯები. თითოეული მათგანი იგივე ფორმის ამოცანაა (რაღაც მოხდა, ფული გადაადგილდა, ვიღაცას სჭირდება ამის ნახვა ანგარიშგებაში), და საერთო საძირკვლის გარეშე, თითოეული იქცევა საკუთარ ერთჯერად ცხრილად და საკუთარ ერთჯერად რეპორტად. `financial_events` + `accounts`/`journal_entries`/`journal_lines` (`src/modules/ledger` მოდული და სამი გვერდი — Summary `/`-ზე, ანგარიშთა გეგმა `/accounts`-ზე, ჟურნალი `/journal`-ზე) არის ეს საერთო საძირკველი, დამატებული სავალდებულო დეშბორდის ერთი ხაზის შეხების გარეშეც კი. ეს არის **რეკომენდაცია საბუღალტრო/ფინანსური პერსონალისთვის შესაფასებლად, არა უკვე მიღებული გადაწყვეტილება** — სრული დასაბუთებისთვის, მათ შორის რას არ ცდილობს ჯერ გადაწყვიტოს, იხ. `docs/ARCHITECTURE.md` (ან [ARCHITECTURE.ka.md](./docs/ARCHITECTURE.ka.md)).

ის ახლა აპლიკაციის ნაგულისხმევი მთავარი გვერდია, რომ იოლად განსახილველი იყოს; სავალდებულო დეშბორდი გადავიდა `/reconciliation`-ზე, sidebar-ის ჩარჩოიანი ბმულით ხელმისაწვდომი. კოდის დამოკიდებულება ცალმხრივი რჩება: `/reconciliation`-ის კოდი არაფერს არ იმპორტავს `src/modules/ledger`-იდან და იდენტურად იმუშავებდა, სქაფოლდის სრულად წაშლის შემთხვევაშიც.

Setup ფაილების თანმიმდევრობით გაშვება მას აყენებს — არაფერია საბექფილო, ყოველი გატარება ხდება ცოცხლად, insert-ის დროსვე. უსაფრთხოა მთლიანად გამოტოვება ან თავიდან გაშვება. მოგვიანებით წასაშლელად, გაუშვით `supabase/drop_ledger_branch.sql` (სავალდებულო დეშბორდის ცხრილებს არასდროს ეხება) — უბრალოდ გაითვალისწინეთ, რომ ამის შემდეგ `/`-ს არაფერი ექნება წასაკითხი, ასე რომ დაგჭირდებათ sidebar-ის ბმულის გადამისამართება ან პირდაპირ `/reconciliation`-ზე ნავიგაცია.

### სამსაფეხურიანი ledger-მოდელი

| საფეხური                     | ტრიგერი                         | გატარება                                                              | ეფექტი                                                                                                          |
| ---------------------------- | ------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 1. ხელშეკრულება შექმნილია    | `INSERT` on `contracts`         | `Dr 1410 მოთხოვნები` / `Cr 6000 შემოსავალი`, თითო აქტიურ თვეზე ერთხელ | მოთხოვნა და შემოსავალი იზრდება ყოველ თვეს, სანამ ხელშეკრულება აქტიურია, არა ერთდროულად                          |
| 2. ტრანზაქცია იმპორტირებულია | `INSERT` on `bank_transactions` | `Dr 1490 დაუდგენელი` / `Cr 6110 არა იდენტ. შემოსავალი`                | ბანკის მიერ მიღებული თანხა მაშინვე ჩანს, დადგენამდე                                                             |
| 3. ტრანზაქცია დამთხვეულია    | `status = 'matched'`            | `Dr 1210 BOG` / `Cr 1490` და `Dr 6110` / `Cr 1410`                    | ნაღდი ფული გადადის suspense-იდან; მოთხოვნა იფარება მე-2 საფეხურის suspense-შემოსავლის წინააღმდეგ, არა `6000`-ის |

ინვარიანტი ყოველთვის მოქმედებს: `sum(bank_transactions.amount) = balance(1210) + balance(1490)` ("იმპორტირებული = დამთხვეული + დაუდგენელი"). შემოწმება:

```sql
select
  (select coalesce(sum(amount), 0) from bank_transactions) as imported,
  (select balance from account_balances where code = '1210') as matched_bog,
  (select balance from account_balances where code = '1490') as undefined_transactions;
```

`1410` იწერება ერთხელ თითო კალენდარულ თვეზე, სანამ ხელშეკრულება აქტიურია (არა ერთხელ ხელშეკრულებაზე), იმეორებს დეშბორდის საკუთარ `isContractActiveInMonth()` წესს — მათ შორის შეჩერებული/დასრულებული ხელშეკრულებებისთვის, რომელთა წარსული თვეები ინარჩუნებენ მოთხოვნას. დარჩენილი შეზღუდვებისთვის იხ. [`docs/ARCHITECTURE.ka.md`](./docs/ARCHITECTURE.ka.md), ხოლო მისი ხუთი-საფეხურიანი ვიზუალისთვის — ეს ხუთი setup საფეხური ეკრანზე, თვე-თვის მიხედვით.

### Ledger UI-ის შენიშვნები

- `/` და `/journal` ნაგულისხმევად აჩვენებს ბოლო 4 თვიდან უახლესს (იგივე, რაც `/reconciliation`) — "ყველა თვის" ხედი აღარ არსებობს. `/`-ზე, `1410` მაინც აჩვენებს ჭეშმარიტ კუმულაციურ ბალანსს, არჩეული თვის მიუხედავად (იხ. `computeAccountBalances()`); `/journal`-ზე, 4 თვეზე ძველი ჩანაწერები უბრალოდ არ ჩანს, თუმცა ყველგან სხვაგან მაინც ითვლება.
- `/journal` პაგინირებულია — 25 ჩანაწერი გვერდზე, რადგან ერთ თვეს შეუძლია რამდენიმე ასეული ჩანაწერის შენახვა, ხელშეკრულების მოთხოვნისა და ტრანზაქციის გატარებების ერთობლიობით.
