# გადახდების შედარების დეშბორდი (Payment Reconciliation Dashboard)

🇬🇧 [English version](./README.md)

დეშბორდი, რომელიც შედარებს Bank of Georgia-ს ტრანზაქციებს აქტიურ მომსახურების ხელშეკრულებებთან — გადახდებს უსადაგებს კომპანიებს, აჩვენებს დაუდგენელს და ადარებს მოსალოდნელ და ფაქტობრივ შემოსავალს თვეების მიხედვით.

**Live:** [gs-reconciliation.vercel.app](https://gs-reconciliation.vercel.app/)

## სტეკი

- Next.js 15 (App Router) + TypeScript
- Supabase (Postgres + PostgREST + RPC)
- TanStack Query
- Tailwind CSS v4
- Zod

## გამართვა და ლოკალურად გაშვება

### 1. დამოკიდებულებების ინსტალაცია

```bash
npm install
```

### 2. Supabase პროექტის შექმნა

გახსენით [supabase.com](https://supabase.com), შექმენით უფასო-დონის პროექტი და დაელოდეთ მის მზადყოფნას.

### 3. SQL ფაილების გაშვება — თანმიმდევრობით, თითო-თითოდ

გახსენით **SQL Editor** თქვენს Supabase დეშბორდში. ყოველი ფაილისთვის გახსენით **ახალი query ტაბი**, ჩასვით შიგთავსი და დააჭირეთ **Run**-ს. (რამდენიმე ფაილის ერთ ტაბში ჩასმა იწვევს იმას, რომ რედაქტორი ჩუმად უშვებს მხოლოდ ბოლო statement-ს.)

1. `seed_schema.sql` — ქმნის `companies`, `contracts`, `bank_transactions` ცხრილებს, ინდექსებს და `updated_at` ტრიგერს; ავსებს 15 კომპანიით და 18 ხელშეკრულებით.
2. `seed_transactions.sql` — ავსებს 89 საბანკო ტრანზაქციით (2026 წლის აპრილი–ივნისი), ყველა `status = 'unmatched'`.
3. `supabase/migrations/001_match_transactions_by_inn.sql` — ქმნის `match_transactions_by_inn()`-ს, Postgres ფუნქციას **"მატჩინგის გაშვება"** ღილაკის მიღმა.
4. მიეცით `anon`-ს execute უფლება და გამორთეთ RLS (საჭიროა anon key-ის გამოსაყენებლად ავტორიზაციის გარეშე):
   ```sql
   GRANT EXECUTE ON FUNCTION match_transactions_by_inn() TO anon;
   ALTER TABLE companies DISABLE ROW LEVEL SECURITY;
   ALTER TABLE contracts DISABLE ROW LEVEL SECURITY;
   ALTER TABLE bank_transactions DISABLE ROW LEVEL SECURITY;
   ```
5. **რეკომენდებული, არასავალდებულო:** `supabase/migrations/002_add_transaction_comment.sql` — ამატებს არასავალდებულო `comment` სვეტს `bank_transactions`-ს. ფრონტენდი გაშვების დროს ავტომატურად ამოწმებს, არსებობს თუ არა ეს სვეტი და "კომენტარი" სვეტი/რედაქტორი მხოლოდ იმ შემთხვევაში აჩვენებს, თუ არსებობს — ამ ნაბიჯის გამოტოვება უსაფრთხოა, აპლიკაცია მის გარეშეც მუშაობს. მაინც ღირს გაშვება: 89 და-seed-ულ ტრანზაქციაში 12-ს აქვს გამგზავნის საიდენტიფიკაციო კოდი, რომელიც არცერთ კომპანიას არ ეკუთვნის (`select match_transactions_by_inn();` ამთხვევს 77-ს, დარჩენილი 12 რჩება `unmatched`), და არც ხელშეკრულება არსებობს ერთის შესათავაზებლად. კომენტარი ერთადერთი ადგილია, სადაც ჩაიწერება, _რატომ_ — მაგ. "ბანკთან დადასტურებული, ერთჯერადი გადახდა, არა ხელშეკრულება" ან "უცნობი გამგზავნი, მონიშნული შემდგომი შემოწმებისთვის 2026-07-02" — რომ შემდეგმა ოპერატორმა, ვინც ამ მწკრივს ხედავს, თავიდან არ დაუწყოს გამოძიება.

გამოწმება: `select count(*) from bank_transactions;` უნდა დააბრუნოს 89, ხოლო `select match_transactions_by_inn();` — 77 (77 დამთხვეული, 12 რჩება `unmatched` — ამ 12-ს აქვს გამგზავნის საიდენტიფიკაციო კოდი, რომელიც არცერთ თესლადებულ კომპანიას არ ეკუთვნის).

### 4. გარემოს ცვლადების გამართვა

დააკოპირეთ `.env.local.example` `.env.local`-ად და შეავსეთ თქვენი Supabase პროექტის URL და anon/publishable key (**Project Settings → Data API**):

```

NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-or-publishable-key
```

გახსენით [http://localhost:3000](http://localhost:3000). მატჩინგის ღილაკის თავიდან შესამოწმებლად, ხელახლა გაუშვით `seed_transactions.sql` (ყველა 89 მწკრივს უბრუნებს `unmatched`-ზე) და დააჭირეთ **"მატჩინგის გაშვება"**-ს.

## სქემა

იხ. `seed_schema.sql` სრული DDL-ისთვის. შეჯამება:

- **companies** — `id`, `name`, `tax_id` (უნიკალური)
- **contracts** — `id`, `company_id` (FK), `monthly_amount`, `status` (`active`/`paused`/`ended`), `start_date`, `end_date` (nullable)
- **bank_transactions** — `id`, `doc_key` (უნიკალური დედუპ-გასაღები), `entry_date`, `amount`, `sender_name`, `sender_inn`, `matched_company_id` (FK, nullable), `match_method`, `match_confidence`, `status` (`matched`/`unmatched`/`ignored`)

## სადაა მოთავსებული მატჩინგის ლოგიკა და რატომ

**ის მოთავსებულია ბაზაში**, როგორც Postgres ფუნქცია (`match_transactions_by_inn()`), გამოძახებული Supabase RPC-ის საშუალებით ღილაკზე დაჭერისას.

მე თავს ავარიდებდი მატჩინგის ლოგიკის კლიენტის მხარეს იმპლემენტაციას, რადგან ფინანსური შედარება უნდა იყოს სანდო და არ შეიძლება ეყრდნობოდეს კლიენტის-მხარის კოდს. აპლიკაციის სერვერსა და PostgreSQL-ს შორის, ბირთვულ შედარების ალგორითმს PostgreSQL-ში მოვათავსებდი, რადგან ის ძალიან ეფექტურად ასრულებს join-ებს და ტრანზაქციულ განახლებებს. Next.js სერვერი გაუმკლავდებოდა ავთენტიფიკაციას, ავტორიზაციას, შეყვანის ვალიდაციას, აუდიტის ჟურნალირებას და ბაზის ფუნქციის გამოძახებას. ეს გამიჯვნა ინარჩუნებს ბიზნეს-პროცესს უსაფრთხოს, პროდუქტიულს და შენარჩუნებადს, ამავდროულად სარგებლობს PostgreSQL-ის ტრანზაქციული გარანტიებით.

მატჩინგის წესი — `bank_transactions.sender_inn = companies.tax_id` — ერთი თანასწორობის join-ია. არ არსებობს მრავალსაფეხურიანი განშტოება, გარე API გამოძახება, ან რამე, რაც სარგებელს მოიტანდა აპლიკაციის კოდში გამოსახვით.

**რატომ ეს მიდგომა:**

- **ატომურობა** — მთელი მატჩინგის გაშვება ერთი SQL statement-ია. კლიენტის-მხარის იმპლემენტაციას (ყველაფრის fetch, JS-ში შედარება, N update-ის გაშვება) აქვს რეალური ჩავარდნის სცენარი, სადაც ქსელის შეფერხება ციკლის შუაში ტოვებს მონაცემთა ნაკრებს ნახევრად-დამთხვეულს, ტრანზაქციის საზღვრის გარეშე. RPC ან სრულად სრულდება, ან საერთოდ არა.
- **წარმადობა** — ერთი მიმოსვლა N-ის ნაცვლად. 89 მწკრივისთვის ეს თითქმის არ აქვს მნიშვნელობა; რეალურ მასშტაბზე (ბანკის feed-იდან ყოველდღიურად ათასობით ტრანზაქცია) კი დიდი მნიშვნელობა აქვს.
- **იდემპოტენტურობა** — ფუნქცია ეხება მხოლოდ იმ მწკრივებს, სადაც `status = 'unmatched'`. ღილაკზე ხელახლა-ხელახლა დაჭერა უსაფრთხოა. უკვე-დამთხვეულ მწკრივებს არასდროს ეხება ხელახლა. ხელით `ignored`-ად მონიშნულ ტრანზაქციებსაც არასდროს გადაწერს — ეს სტატუსი წარმოადგენს ადამიანურ გადაწყვეტილებას და ავტომატურმა მატჩინგმა არ უნდა ჩუმად გააუქმოს ის.
- **ქმედითი ჩავარდნის სცენარი** — თუ `match_transactions_by_inn()` ჯერ არ შექმნილა (migration 001 გამოტოვებული, ან `EXECUTE` არასდროს მიცემულა `anon`-ისთვის), RPC გამოძახება ჩავარდება PostgREST-ის "ფუნქცია ვერ მოიძებნა" შეცდომით. სერვისის ფენა (`src/services/transaction.service.ts`) ცნობს ამ კონკრეტულ შეცდომას და "მატჩინგის გაშვება" ღილაკი აჩვენებს ქმედით შეტყობინებას, რომელიც ეუბნება ოპერატორს, გაუშვას migration, ზოგადი/ჩუმი ჩავარდნის ნაცვლად.

**გულწრფელი კომპრომისი:** ეს ლოგიკა უხილავია ვინმესთვის, ვინც მხოლოდ Next.js კოდბაზას კითხულობს, და უფრო რთულია იზოლირებულად unit-ტესტირება, ვიდრე უბრალო TypeScript ფუნქცია. ეს მისაღები ხარჯია აქ, რადგან ოპერაცია პატარა და ერთი-დანიშნულებისაა. თუ ბუნდოვანი ან ხელით-მატჩინგის ლოგიკა მნიშვნელოვნად გაიზრდება, ეს სიგნალია მატჩინგის აპლიკაციის ფენაში დასაბრუნებლად — რაც ზუსტად იმის მიზეზია, რომ ხელით-მატჩინგის გზა (და მისი ბუნდოვანი-შემოთავაზების ქულა) ცხოვრობს აპლიკაციაში, არა ბაზაში.

## მოსალოდნელი vs. ფაქტობრივი: მთავარი წესი

ხელშეკრულება ითვლება აქტიურად თვის M განმავლობაში, თუ:

- `start_date <= M-ის ბოლო დღე` და
- `end_date IS NULL ან end_date >= M-ის პირველი დღე`

ეს სწორად ამუშავებს edge case-ებს თესლის მონაცემებში:

- **სეიფ ტრანსპორტი** (`end_date = 2026-05-15`): ითვლება აქტიურად აპრილში და მაისში, გამოვარდება ივნისში
- **ურბან მუვერსი** (`end_date = 2026-04-30`): ითვლება აპრილში, გამოვარდება მაისში და ივნისში
- **ეკო ტრანსპორტი** (ორი პარალელური აქტიური ხელშეკრულება: 750 + 1100/თვეში): მოსალოდნელი თანხა ჯამდება, არა ერთი მწკრივიდან აღებული

## მონაცემების ჩატვირთვა, ქეშირება და მუტაციები

**ჩატვირთვა** — ყოველი წაკითხვა (კომპანიები, ხელშეკრულებები, ტრანზაქციები) გადის TanStack Query-ს საშუალებით, ცენტრალიზებული query key ფაბრიკის მეშვეობით (`src/lib/query/queryKeys.ts`), რომ ქეშის ინვალიდაციამ ჩუმად ვერ გამოტოვოს გასაღები. თითოეულ კომპონენტს აქვს საკუთარი `isLoading` მდგომარეობა და აჩვენებს skeleton-ს (`StatsBar`, `TransactionsTable`, `ExpectedVsActual` — ყველას აქვს) ცარიელი ეკრანის ნაცვლად.

**ქეშირება** — კომპანიები და ხელშეკრულებები იშვიათად იცვლება, ამიტომ იყენებენ 5-წუთიან `staleTime`-ს. ტრანზაქციები განსხვავებულია: ისინი იცვლება მხოლოდ მუტაციის საშუალებით, რომელსაც ეს აპლიკაცია აკონტროლებს (არ არსებობს გარე პროცესი, რომელიც წერს `bank_transactions`-ში დეშბორდის ღია ყოფნისას), ამიტომ `useTransactions` აყენებს `staleTime: Infinity`-ს და მთლიანად ეყრდნობა მუტაცია-გამოწვეულ ქეშის ინვალიდაციას, საათის ნაცვლად. პრაქტიკულად, ეს ნიშნავს, რომ სესიაში უკვე მონახულებულ თვის ტაბებს ან სტატუსის ფილტრებს შორის გადართვა ემსახურება ქეშიდან **ქსელური მოთხოვნების გარეშე** — ის ხელახლა იტვირთება მხოლოდ ნამდვილად ახალი ფილტრი/თვის კომბინაციისთვის. `placeholderData: keepPreviousData` დამატებით ინახავს წინა მწკრივებს ეკრანზე ახალი კომბინაციის ჩატვირთვის დროს, ასე რომ ცხრილი განახლდება ადგილზე, loading skeleton-ზე ციმციმის ნაცვლად ყოველ ფილტრის ცვლილებაზე თუ კლავიშზე დაჭერაზე (ძიებაც debounce-ილია კლიენტის მხარეს, სანამ query-ს მიაღწევს, ასე რომ აკრეფა არ იწვევს მოთხოვნას თითო სიმბოლოზე).

**მუტაციები** — ყოველი ჩაწერა გადის `src/hooks/useTransactionMutations.ts`-ის საშუალებით:

- `useRunAutoMatching` — უშვებს `match_transactions_by_inn()` RPC-ს
- `useManuallyMatchTransaction` / `useUnmatchTransaction` — ანიჭებს ან შლის ხელით მატჩს კომპანიასთან
- `useUpdateTransactionStatus` — ignore / un-ignore ტრანზაქცია
- `useUpdateTransactionComment` — თავისუფალი-ტექსტის კომენტარის შენახვა

ამათგან ნებისმიერს შეუძლია ტრანზაქცია გადაიტანოს `matched` / `unmatched` / `ignored`-ს შორის, რაც ცვლის, რომელ ფილტრირებულ ხედს ეკუთვნის ის. ყოველი ქეშირებული ფილტრის კომბინაციის ზუსტად ჩასწორების ნაცვლად, ყოველი მუტაცია იძახებს `invalidateQueries({ queryKey: queryKeys.transactions.all })`-ს — რადგან `["transactions"]` არის ყოველი `["transactions", "list", filters]` გასაღების პრეფიქსი, ეს სწორად აბათილებს ყველა ფილტრირებულ ხედს (სრული ხედი, "მხოლოდ დაუდგენელი" ხედი და ა.შ.) ერთი გამოძახებით. ზემოთხსენებულ `staleTime: Infinity`-სთან ერთად, ეს ერთადერთია, რაც ტრანზაქციების ხელახლა-ჩატვირთვას იწვევს: რეალური მონაცემების ცვლილება, არა გასული დრო.

## არქიტექტურის შენიშვნები

- **service layer** (`src/services/`): ერთი typed ფაილი თითო ცხრილზე, Supabase-ს პირდაპირ ახვევს. არ არსებობს ცალკე repository ფენა — სამი ცხრილითა და თხელი query builder-ით, დამატებითი ფენა იქნებოდა indirection ქცევითი განსხვავების გარეშე. Raw `NUMERIC` სვეტები PostgREST-იდან მოდის სტრიქონებად (ფასის მნიშვნელობებზე float-ის სიზუსტის დაკარგვის თავიდან ასაცილებლად) და გარდაიქმნება `number`-ად ერთხელ, სერვისის საზღვარზე.
- **`src/types/database.ts`**: ხელით დაწერილი, რომ ასახავდეს `seed_schema.sql`-ს. შეიცავს `Relationships: []`-ს თითოეულ ცხრილზე და `__InternalSupabase` მარკერს — ორივე საჭიროა ბოლოდროინდელი `@supabase/supabase-js` ვერსიებისთვის, რომ `.update()`-ის არგუმენტის ტიპები სწორად გადაწყდეს. მათი გამოტოვება ჩუმად აფართოებს იმ ტიპებს `never`-მდე.
- **Zod**: ვალიდაციას უკეთებს ფილტრის/ძიების/დახარისხების მდგომარეობას `src/schemas/transactionFilters.ts`-ში.
- **ფიქსირებული-სიგანის ცხრილის სვეტები**: `TransactionsTable` იყენებს `table-layout: fixed`-ს ცხადი `<colgroup>`-ით, ასე რომ გრძელი გამგზავნის სახელი, კომენტარი ან კომპანიის სახელი მოიკვეცება ellipsis-ით, სხვა ყველა სვეტის სიგანის შეცვლის ნაცვლად მწკრივების ხელახლა-რენდერისას.
