# შედარების ხელსაწყოდან ფინანსურ პლატფორმამდე

🇬🇧 [English version](./ARCHITECTURE.md)

**ბრენჩის ფარგლები:** ეს დოკუმენტი და `ledger` მოდული, რომელსაც ის აღწერს, არის **რეკომენდაცია**, არა გადაწერა. საწყისი დავალების ყველა მოთხოვნა ისევ ისე მუშაობს, უბრალოდ გადატანილია `/reconciliation`-ზე. ეს ბრენჩი მატებს მეორე, დანამატ ფენას, რომელიც აჩვენებს, როგორ შეიძლება კოდბაზა გაიზარდოს უფრო ფართო ფინანსურ პლატფორმად (ინვოისები, ხელფასები, ხარჯები, საერთო ჟურნალი), გადაწერის გარეშე.

ის მიზანმიმართულად პატარაა: რამდენიმე ცხრილი, არსებულის მსგავსი სერვის/hook ფენა და სამი გვერდი — Summary (`/`), ანგარიშთა გეგმა (`/accounts`), ჟურნალი (`/journal`) — პლუს ერთი ცოცხალი მოქმედება (იგივე მატჩინგის მუტაციის ხელახლა-გაშვება, რაც დეშბორდს უკვე აქვს).

## 1. რატომ არა უბრალოდ მეტი ცხრილი

ყოველი ახალი ფულის-გადაადგილების ფუნქციისთვის (ქირა, ხელფასები, ინვოისები) დანიშნულებითი ცხრილის მიმატება `bank_transactions`/`contracts`-ზე ნიშნავს, რომ ყოველი "რამდენი ფული გადაადგილდა" რეპორტი საბოლოოდ ხელით აკეთებს `UNION`-ს ცხრილებზე, რომლებიც არასდროს იყო შექმნილი ერთმანეთთან გასაერთიანებლად.

გამოსავალი არ არის სრული ორმაგი ჩაწერის ბუღალტერია პირველივე დღიდან — ეს ნამდვილი სირთულეა, რაც ამ დავალებას არ სჭირდება. გამოსავალია ყოველ დომენს მიეცეს **ერთი საერთო, მხოლოდ-დამატების ადგილი "მოხდა ფინანსური მოვლენა"-ს ჩასაწერად**, სადაც ორმაგი ჩაწერა არის **არასავალდებულო ფენა ამის თავზე**, მიღებული თითო მოვლენის ტიპზე, მხოლოდ მაშინ, როცა რეალურად საჭიროა GL-დონის რეპორტინგი.

## 2. შემოთავაზებული სქემა

სამი ახალი, სრულად დანამატი ცხრილი. არაფერი აქ არ ცვლის `companies`-ს, `contracts`-ს ან `bank_transactions`-ს.

**`financial_events`** — ერთადერთი წყარო ჭეშმარიტებისა, რომელშიც ყოველი დომენი წერს:

```sql
create table financial_events (
  id uuid primary key default gen_random_uuid(),
  source_type text not null,        -- 'bank_transaction' | 'invoice' | 'expense' | 'payroll' | 'manual' | ...
  source_id uuid not null,          -- id of the row in the source domain table
  occurred_at date not null,
  amount numeric(15,2) not null,
  direction text not null check (direction in ('inflow', 'outflow')),
  description text,
  created_at timestamptz not null default now(),
  unique (source_type, source_id)   -- one event per source row, idempotent to re-run
);
```

`source_type` + `source_id` არის რბილი მაჩვენებელი (არა foreign key, რადგან სხვადასხვა ცხრილზე მიუთითებს თითო მწკრივზე) იმ დომენ-ცხრილისკენ, რომელიც ფლობს ჩანაწერს. ახალი დომენი მატებს ცხრილს პლუს ერთ ადაპტერს, რომელიც წერს აქ იმ მოვლენებზე, რომლებიც მას აინტერესებს — ის არასდროს ეხება სხვა დომენის ცხრილებს.

**არასავალდებულო ორმაგი ჩაწერის ფენა:**

```sql
create table accounts (
  id uuid primary key default gen_random_uuid(),
  code text unique not null,
  name text not null,
  type text not null check (type in ('asset','liability','equity','revenue','expense')),
  normal_balance text not null check (normal_balance in ('debit','credit')),
  is_active boolean not null default true
);

create table journal_entries (
  id uuid primary key default gen_random_uuid(),
  financial_event_id uuid references financial_events(id),  -- nullable: posting is optional
  entry_date date not null,
  description text
);

create table journal_lines (
  id uuid primary key default gen_random_uuid(),
  journal_entry_id uuid not null references journal_entries(id) on delete cascade,
  account_id uuid not null references accounts(id),
  debit numeric(15,2) not null default 0 check (debit >= 0),
  credit numeric(15,2) not null default 0 check (credit >= 0),
  check (not (debit > 0 and credit > 0))
);
```

`financial_event_id` არასავალდებულოა (`nullable`), რადგან ledger-ში გატარება არის ის, რასაც მოვლენას _შეუძლია_ გამოიწვიოს, არა ის, რაც _უნდა_ გამოიწვიოს. ტრანზაქცია შეიძლება შედარდეს და ჩაითვალოს მოსალოდნელი-vs-ფაქტობრივში, ჟურნალის ჩანაწერად ქცევის გარეშეც.

**რას იძლევა ეს:**

| მომავალი ფუნქცია | რა უნდა დაემატოს | რას არ სჭირდება შეხება |
|---|---|---|
| ინვოისები | `invoices` ცხრილი + ერთი ადაპტერი | `bank_transactions`, შედარების UI, ledger სქემა |
| ხელფასები | `payroll_runs`/`payroll_lines` + ერთი ადაპტერი | ყველაფერი ზემოთ |
| "ფულადი პოზიცია ყველა წყაროზე" | ერთი query `financial_events`-ზე | არაფერი |
| საცდელი ბალანსი | query `journal_lines`-ზე, ანგარიშის მიხედვით დაჯგუფებული | არაფერი — უკვე სწორი ფორმაა |

## 4. როგორ უკავშირდება `/` `/reconciliation`-ს

სამი ledger-გვერდი იზიარებს `AppSidebar` → `LedgerSidebar`-ს (მხოლოდ ნავიგაცია) → `LedgerNav`-ს, რომელიც ასევე ჩამოთვლის ჯერ-არ-აშენებულ დომენებს (მომხმარებლები, ინვოისები, ხელფასები და ა.შ.) გამორთულ ელემენტებად.

- **Summary** (`/`) — ბალანსი + მოგება-ზარალი, გადათვლილი კლიენტის მხარეს, არჩეული თვის მიხედვით.
- **ანგარიშთა გეგმა** (`/accounts`) — 16 თესლადებული ანგარიში.
- **ჟურნალი** (`/journal`) — ყოველი გატარება არჩეული თვისთვის, პაგინირებული 25/გვერდზე (ერთ თვეს შეუძლია რამდენიმე ასეული ჩანაწერის შენახვა).

სამივე გვერდი მხოლოდ _კითხულობს_. ერთადერთი ჩაწერის გზა, `LedgerMatchButton`, არ არის მეორე მატჩინგის იმპლემენტაცია — ის იძახებს იმავე `useRunAutoMatching` მუტაციას, რასაც `/reconciliation`-ის ღილაკი, გამოსახული `/`-ის საკუთარ header-ში (ზემოთ-მარჯვნივ, იმავე ადგილას, სადაც `/reconciliation`-ის ასლია). რადგან ღილაკი და `LedgerNav`-ის "+N" ბეჯი არიან და-ძმები `app/layout.tsx`-ის ქვეშ, არა მშობელი/შვილი, "მატჩი ახლახან განხორციელდა" სიგნალი გადის `MatchHighlightContext`-ის საშუალებით, prop-ის ნაცვლად.

ყოველი ჟურნალის ჩანაწერი უბრუნდება სამი რეალური მოვლენიდან ერთს, თითოეული გამოქვეყნებული **ბაზის ტრიგერით**, რომელიც რეაგირებს მწკრივის ცვლილებაზე — არასდროს აპლიკაციის კოდში დამატებული ფუნქციის გამოძახებით, ამიტომ შედარების აპლიკაციას წარმოდგენა არ აქვს ledger-ის არსებობის შესახებ:

| საფეხური | ტრიგერი | გატარება | ეფექტი |
|---|---|---|---|
| 1. ხელშეკრულება შექმნილია | `AFTER INSERT` on `contracts` (`post_contract_demand()`) | `Dr 1410 მოთხოვნები` / `Cr 6000 შემოსავალი`, თითო აქტიურ თვეზე ერთხელ | მოთხოვნა და შემოსავალი იზრდება ყოველ თვეს, სანამ ხელშეკრულება აქტიურია. არ არის დამოკიდებული `status`-ზე — შეჩერებული/დასრულებული ხელშეკრულება ინარჩუნებს წარსული თვეების მოთხოვნას. |
| 2. ტრანზაქცია იმპორტირებულია | `AFTER INSERT` on `bank_transactions` (`post_transaction_import()`) | `Dr 1490 დაუდგენელი` / `Cr 6110 არა იდენტ. შემოსავალი` | ბანკის მიერ მიღებული თანხა მაშინვე ჩანს, დადგენამდე. |
| 3. ტრანზაქცია დამთხვეულია | `status = 'matched'` (`post_transaction_match()`) | `Dr 1210 BOG` / `Cr 1490` **და** `Dr 6110` / `Cr 1410` | ნაღდი ფული გადადის suspense-იდან; მოთხოვნა იფარება მე-2 საფეხურის suspense-შემოსავლის წინააღმდეგ, არა `6000`-ის (რომელმაც ეს შემოსავალი უკვე ერთხელ ცნო, პირველ საფეხურზე). დამთხვევის გაუქმება შლის მხოლოდ ამ გატარებას. |

ინვარიანტი ყოველთვის მოქმედებს: `sum(bank_transactions.amount) = balance(1210) + balance(1490)` ("იმპორტირებული = დამთხვეული + დაუდგენელი") — მე-2 საფეხური ყოველ იმპორტირებულ თანხას წერს `1490`-ში, მე-3 საფეხური მხოლოდ _ატარებს_ ფულს `1210`-სა და `1490`-ს შორის.

`useRunAutoMatching`/`useManuallyMatchTransaction`/`useUnmatchTransaction` ასევე აბათილებს ledger-ის TanStack Query key-ებს, ტრანზაქციების key-სთან ერთად, რადგან ბაზის ტრიგერის გამოძახება თავისთავად არაფერს ეუბნება კლიენტის ქეშს.

**გულწრფელი კომპრომისები:** ბაზის ტრიგერი უჩინარია TypeScript კოდიდან (იგივე კრიტიკა, რასაც README უკვე აკეთებს `match_transactions_by_inn()`-ზე), და დამთხვევის გაუქმება შლის-და-ხელახლა-წერს მე-3 საფეხურს, არა აბრუნებს — მისაღებია დემოსთვის, არა რეალური აუდიტისთვის.

**თვის ფილტრი და პაგინაცია:** `/` და `/journal` ნაგულისხმევად აჩვენებს ბოლო 4 თვიდან უახლესს, იგივე რაც `/reconciliation` — "ყველა თვის" ხედი არ არსებობს. `/`-ზე, `1410` მაინც აჩვენებს ჭეშმარიტ კუმულაციურ ბალანსს არჩეული თვის მიუხედავად (`computeAccountBalances()` კითხულობს ყველა წამოღებულ ჩანაწერს, არა მხოლოდ იმ თვისას); ყოველი სხვა ანგარიში აჩვენებს მხოლოდ იმ თვის აქტივობას. `/journal`-ზე, 4 თვეზე ძველი ჩანაწერები აღარ ჩანს, თუმცა ყველგან სხვაგან მაინც ითვლება. `/journal` დამატებით პაგინირდება კლიენტის მხარეს (25/გვერდზე) თვის ფილტრის თავზე — `useJournalEntries()` მაინც წამოიღებს ყველაფერს გაუფილტრავად, რადგან `/`-ს სჭირდება სრული ნაკრები კუმულაციური ბალანსისთვის; მხოლოდ ის, რაც იხატება, შეკვეცილია.

`seed_demo_opening_balance.sql` არის არასავალდებულო, არა-საწარმოო **მესამე** setup ფაილი — გაშვებული `seed_contracts.sql`-ის შემდეგ, `seed_transactions.sql`-მდე — რომელიც წერს `1410`-ის ფანჯრამდელ ბალანსს, რომ ეკრანზე რიცხვები წაკითხვადი დარჩეს იმ მომენტიდან, დიდი შეუსწორებელი ჯამის ნაცვლად ბოლო ფაილის გაშვებამდე. მათემატიკისთვის იხ. ფაილის საკუთარი header, ეკრანზე გამოსახულებისთვის კი — ქვემოთ მოცემული ვიზუალი.

## 5. აშკარა არა-მიზნები

- არა სრული ბუღალტრული სისტემა: არ არის პერიოდის დახურვა, საცდელი ბალანსის რეპორტი, მრავალვალუტიანობა, აუდიტის ჟურნალი.
- არ ხდება გატარებების **გაუქმება** დამთხვევის მოხსნისას (შლის მე-3 საფეხურის გატარებას მის ნაცვლად) — რეალური სისტემა გააუქმებდა, არა წაშლიდა.
- არ არის UI ანგარიშების ან ჟურნალის ჩანაწერების ხელით შესაქმნელად/სარედაქტირებლად — ყველაფერი იწერება სამი ტრიგერით.
- არ არის debit = credit ინვარიანტის უზრუნველყოფა ერთ-ხაზიანი `CHECK`-ის მიღმა — თითო-ჩანაწერიანი ბალანსის შემოწმება არის შემდეგი რეალური ნაბიჯი.
- არ არის ანგარიშის არჩევის ლოგიკა — ყოველი ხელშეკრულება/ტრანზაქცია იწერება იმავე სამ ანგარიშზე, კომპანიის მიუხედავად. `financial_events.source_id` უკვე მიუთითებს კონკრეტულ მწკრივზე, ასე რომ კომპანია-სპეციფიკური დაშლა არის `JOIN`, არა სქემის ცვლილება.
- მატჩინგი არის ყველაფერი-ან-არაფერი თითო მწკრივზე — ერთი ტრანზაქციის ორ ხელშეკრულებაზე გაყოფა შეუძლებელია.
- `1410` იწერება ერთხელ თითო აქტიურ კალენდარულ თვეზე, არა სრული ინვოისების ქვე-ჟურნალი — არ არის ვადები, საკრედიტო შენიშვნები ან ნაწილობრივი პერიოდის პროპორცია. მატჩინგი იფარება `1410`-ის საერთო ბალანსის წინააღმდეგ, არა კონკრეტული თვის ჩანაწერის.
- მხოლოდ `INSERT` `contracts`-ზეა მიერთებული — ხელშეკრულების `status`-ის შემდგომი ცვლილება უკან არ არეგულირებს წარსულ მოთხოვნას.
